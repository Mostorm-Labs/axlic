# AxLicense

AxLicense is a Windows C++20 command-line client that implements the **local licensing library plane**: one machine-wide Windows DeviceIdentity backed by a non-exportable persisted CNG P-256 key (TPM-first), offline verification and atomic installation of platform-signed credentials with anti-rollback, a local registration association, and a trust keyring. The client itself contains **no network code** and does not require a server: credential delivery, channel transport, RPC orchestration and receipt reporting belong to the consuming host (launcher bridge), which drives axlic exclusively through the `axlic.exe` CLI contract.

## Build and test

The frozen A0 toolchain is CMake 4.4.2, Visual Studio 2022 17.14 / MSVC 14.44, and Windows SDK 10.0.26100.0.

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A x64 -T v143
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

The public commands currently implemented are:

```text
axlic status
axlic entitlement <entitlement_id>
axlic identity
axlic device-register
axlic device-register adopt <axldev_reference>
axlic device-register reset
axlic install <artifact_path> --policy-version <n>
axlic held-version
```

`axlic identity` must be run with machine-state write authority for first establishment. It returns only the public scheme, epoch, and 64-byte P-256 public identity as lowercase hex; provider key names and private material are never part of the CLI contract.

`axlic device-register` reports the dual-state self-report value for the connection identity: the 128-hex `identity_value` while unregistered (or after the local reference was dropped), or the platform-assigned `axldev_` reference once `adopt` has persisted it. `install` runs the frozen pipeline — A0 signature verification, payload device-reference match, `(authority_revision, credential_generation)` lexicographic high-watermark anti-rollback with idempotent same-version reinstall, and an atomic local commit; an empty-entitlements revocation credential is a legal install object. `held-version` returns the held `(authorityRevision, credentialGeneration, policyVersion)` triple (or the no-credential state) for version probes and reconciliation. Channel-transient values such as delivery references never enter axlic.

## Trust keyring

Verification trusts a merged key set: an **embedded trust floor** compiled into the binary at build time, plus a state-root append overlay (`trust-keyring.v1.json`) where an entry with the same `key_id` overrides the floor entry (key rotation replacement). An empty keyring is fail-closed, so nothing verifies until a floor is embedded.

The floor is derived offline from the public key committed for one environment:

| Environment | `key_id` | Public key file | SHA-256 of the DER SubjectPublicKeyInfo |
| --- | --- | --- | --- |
| `test` | `license-test` | `client/keyring/license-test.pub.pem` | `ca7795786820dd5d3d669fb3321b3e11bdafc1cce7d39c4fd59f52e7ef110aea` |
| `prod` | `license-prod` | `client/keyring/license-prod.pub.pem` | `58bb4787245691066105914d20ff3da5da2cb8677b13e943a40f6a73bcc277a8` |

`tools/build_trust_floor.py --environment <test|prod> --out <file>` reads the environment's PEM file, requires its fingerprint to equal the one pinned in the tool, and writes the `axlic-trust-floor` document that CMake embeds. The `key_id` equals the signing-key name the platform writes into every credential. Each artifact embeds its own environment's key only: a production binary rejects credentials signed with the test key, and vice versa; `tools/check_embedded_trust_floor.py` proves that of a built executable.

Only public keys live in this repository. The private keys never leave the signing backend, and no build or publish step needs network access to it. Changing a key changes the trust anchor of every later release: such a change is a reviewed pull request that replaces the PEM file and the fingerprint pinned in `tools/build_trust_floor.py` together.

The checked-in `client/keyring/trust-floor.json` stays the CMake default, so a plain build embeds the empty floor and remains fail-closed. The tooling above is operator tooling only — it is never part of `axlic.exe`, and the binary keeps zero network dependencies (enforced by the offline-boundary import scan).

The checked-in `reference/vectors/a0` corpus and `AXLIC_A0_FIXTURE_STATE` remain explicit test-only A0 regression adapters. Production `axlic.exe` does not read that environment variable. The A2 installation vectors live in `reference/vectors/a2/install.json` and are generated by `reference/tools/a2_reference.py` on top of the same independent reference signer.

## Build a keyed variant

A keyed build embeds one environment's verification key. Pass an absolute path, and keep the document outside the build directory:

```powershell
python tools/build_trust_floor.py --environment test --out build-input/trust-floor.json
cmake -S . -B build -G "Visual Studio 17 2022" -A x64 -T v143 "-DAXLIC_TRUST_FLOOR_FILE=$PWD\build-input\trust-floor.json"
cmake --build build --config Release
python tools/check_embedded_trust_floor.py --environment test --exe build/client/Release/axlic.exe
```

Without `AXLIC_TRUST_FLOOR_FILE` the build embeds the checked-in empty floor. The full `ctest` suite passes on keyed builds as well.

## Publishing

Two GitHub Actions workflows publish `axlic-<version>-win-x64.zip` through one reusable pipeline, `axlic-publish.yml`. The zip holds `axlic.exe`, the app-local VC++ runtime DLLs it imports (`msvcp140.dll`, `vcruntime140.dll`, `vcruntime140_1.dll` — keep them next to the executable), third-party notices with full license texts, `SHA256SUMS.txt` and `build-manifest.json`; its own `.sha256` is published alongside.

- **Release Windows** (`release.yml`): push a `vX.Y.Z` tag whose version equals `project(axlicense VERSION …)` in `CMakeLists.txt` and whose commit is on `main`. To rebuild and re-publish an existing tag, dispatch the workflow with the tag name: the same-named assets are replaced and the tag itself is never moved. Leave `publish` off to rehearse a tag without touching Releases. A production release is a pre-A8 engineering release, not an A8 release-qualification result.
- **Test publish Windows** (`test-publish.yml`): manual only. It builds any ref with the test key and publishes the Pre-release `v<version>-test.<yyyyMMdd>.<run number>`.

Both run the full test suite and the existing evidence steps on the packaged revision, prove that the executable embeds only its environment's key, and re-verify the package after download and before publishing. The workflows read no secret beyond the automatic `GITHUB_TOKEN`. `python tools/package_axlic.py verify --zip <file> --environment <test|prod>` re-checks a downloaded package.
